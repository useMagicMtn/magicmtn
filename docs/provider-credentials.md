# Provider credentials

A provider opts in to protocol version 2 through `package.metadata.magicmtn.protocol-version` in its package metadata. The provider framework's `run_credentialed` helper takes a `CredentialSpec` listing the required JSON fields. The startup frame replaces the v1 Describe request. Discovery sends an empty credential. Preparation sets `verify_account` and the adapter returns an upstream account identifier that is stable across key rotations. Normal startup constructs the authenticated client from the bundle. Sandbox and inference operations use the ordinary RPC frames after initialization.

The local server configures and stores credentials through `magic provider configure`. Providers that implement `ProviderSetup` may idempotently provision account resources during that explicit command; other providers use read-only account verification. See the [provider setup contract](provider-setup.md). It encrypts the credential with AES-GCM and binds the ciphertext to the installation, connection, provider, account, and version. A command is ready once verification, persistence, and publication succeed. An account change requires a separate connection.

An embedding service provisions authorized bindings and prepares credentials before accepting traffic. The `provider_credentials` module provides read-only sources for AWS Secrets Manager with `provider-credentials-aws` and Vault or OpenBao KV v2 with `provider-credentials-vault`. Use the AWS runtime workload identity with a client scoped to the configured secret ARN. For Vault or OpenBao, supply a renewable or agent-managed token file and an HTTPS endpoint. The runtime keeps the store locator and identity in the preparation service.

The Cloud profile uses `provider_account` to pin the upstream identity in the durable credential reference. Before admitting traffic for a binding, the embedding service calls `refresh` or groups matching bindings with `refresh_bindings` for one read per replica and provider account. Run subsequent refreshes in a background task, with a finite maximum staleness. A failed refresh leaves the previous version active until its deadline. Emergency revocation clears the slot, fences any refresh already in progress, and prevents refresh until the operator explicitly enables the binding.

Sandbox creation and command dispatch acquire the prepared client in memory. The host supplies credential bytes in the private startup frame and keys client reuse by the installed pin and immutable resource scope within the active credential version. Publication switches new operations to the replacement and allows already admitted operations to finish.
